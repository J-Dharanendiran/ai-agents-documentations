This video is important because it introduces the **architecture behind

The instructor isn't teaching you how to build a complete agent yet.

# 🧠 1. First, understand what LangGraph actually is

The instructor starts by saying:

> LangGraph is sort of the new way to run agents with LangChain.

Let's unpack that.

You already understand that an AI agent isn't another LLM. It's a system
that uses an LLM to make decisions and perform actions.

For example, imagine building a research agent.

A user asks:

"Find the latest developments in artificial intelligence and summarize
them."

Your system might need to:

1.  Understand the user's request.
2.  Decide whether it needs internet access.
3.  Search the internet.
4.  Read the search results.
5.  Decide whether it needs more information.
6.  Search again if necessary.
7.  Generate a final summary.

Notice something?

The system isn't simply executing a fixed sequence of operations.

**It needs to make decisions about what to do next.**

This is where LangGraph comes in.

LangGraph gives us a framework to define how an agent operates, how its
components communicate, how decisions are made, and how execution moves
between different components.

Think of it this way:

  -----------------------------------------------------------------------
  Technology                          What it helps us build
  ----------------------------------- -----------------------------------
  LangChain                           Individual components, such as
                                      prompts, models, tools and chains

  LangGraph                           The workflow and decision-making
                                      structure that connects those
                                      components
  -----------------------------------------------------------------------

LangGraph is designed for building stateful, cyclic workflows,
particularly AI agents.

# 🕸️ 2. Why is it called LangGraph?

This is probably the most important concept in the video.

The instructor says:

> You've basically got nodes joining to different edges.

To understand this, you need to understand two fundamental concepts:

-   Nodes
-   Edges

Let's start with a simple example.

Imagine we are building an AI research agent.

Its architecture might look like this:

``` text
          User Query
               |
               ▼
         [LLM Node]
               |
               ▼
       Need Internet?
          /       \
        Yes        No
         |          |
         ▼          |
    [Search Tool]   |
         |          |
         ▼          |
    [LLM Node] ◄────┘
         |
         ▼
    Final Answer
```

This is a graph.

It contains:

🧩 **Nodes:** Individual components that perform operations.

🔗 **Edges:** Connections that determine where execution goes next.

Let's understand why this matters.

## 🧩 A. Nodes

A node is an individual component responsible for performing a
particular operation.

For example:

  Node              Responsibility
  ----------------- ---------------------------------------------
  LLM Node          Understands the request and makes decisions
  Search Node       Searches the internet
  Calculator Node   Performs mathematical calculations
  RAG Node          Retrieves relevant information
  Response Node     Generates the final answer

Think of nodes as individual workers in your agent system.

Each worker has a responsibility.

A node can contain: - An LLM call. - A LangChain chain. - A tool
execution. - A Python function. - Any other compatible runnable or
function.

**Important:** A node doesn't necessarily have to be an LLM.

For example, consider this Python function:

``` python
def calculator_node(state):
    result = 10 + 20

    return {
        "result": result
    }
```

This can be a node.

It doesn't require an LLM because the operation is straightforward.

The LLM's job is to decide when the calculator is needed, not
necessarily to perform every calculation itself.

## 🔗 B. Edges

If nodes are individual workers, edges are the connections between those
workers.

They determine where execution moves.

The instructor introduces two important types of edges.

### ➡️ 1. Normal Edges

A normal edge represents a predefined connection.

For example:

``` text
[Retrieve Documents]
         |
         ▼
[Generate Answer]
```

Once the retrieval node finishes, execution automatically moves to the
answer-generation node.

There is no decision involved.

In Python:

``` python
graph.add_edge(
    "retrieve",
    "generate"
)
```

This tells LangGraph:

Whenever the `retrieve` node finishes, execute `generate` next.

### 🔀 2. Conditional Edges

This is where things become interesting.

A conditional edge allows us to determine the next node dynamically.

Consider:

``` text
              [LLM Node]
                   |
                   ▼
            Need a Tool?
              /      \
            Yes       No
             |         |
             ▼         ▼
       [Search Tool] [Final Answer]
             |
             ▼
          [LLM Node]
```

The next node depends on a decision.

For example:

-   If the LLM decides it needs internet access, execute the search
    tool.
-   If it already has sufficient information, generate the final answer.

In LangGraph, conditional edges use a routing function.

Conceptually:

``` python
def decide_next_step(state):

    if state["needs_search"]:
        return "search"

    return "final_answer"
```

Then:

``` python
graph.add_conditional_edges(
    "llm",
    decide_next_step
)
```

**One important clarification:** The conditional edge itself doesn't
have to use an LLM.

The routing function can use: - An LLM's decision. - A tool call
returned by an LLM. - Normal Python conditions. - Information stored in
the current state.

The instructor particularly highlights LLM-based routing.

# 🔁 3. Why does the instructor say LangGraph isn't a DAG?

This is a particularly important distinction.

First, understand two terms.

### 📐 What is a DAG?

DAG stands for Directed Acyclic Graph.

Break that down:

-   Directed: Connections have a particular direction.
-   Acyclic: You cannot return to an earlier node by following the
    connections.

Consider a normal sequential pipeline:

``` text
A → B → C → D
```

Execution moves forward.

It cannot return from D to A.

This is a DAG.

### But AI agents need something different.

Consider our research agent:

``` text
        [LLM]
           |
           ▼
      [Search Tool]
           |
           ▼
        [LLM]
           |
           ▼
   Enough Information?
       /        \
      No        Yes
      |           |
      ▼           ▼
   [Search]    [Finish]
      |
      └──────► [LLM]
```

Notice what happens?

The agent can repeatedly move between the LLM and search tool.

It can:

1.  Think.
2.  Search.
3.  Examine the results.
4.  Think again.
5.  Search again.
6.  Finish when sufficient information is available.

This creates a cycle.

🔁 **The important distinction is that LangGraph supports directed
cycles, unlike a DAG.**

A LangGraph workflow doesn't have to execute each node only once.

This is extremely useful for AI agents because agents often need
multiple rounds of reasoning and tool execution.

# 🗃️ 4. StateGraph: The memory of the workflow

Now we reach one of the most important concepts in the entire video.

The instructor introduces something called `StateGraph`.

He explains that state is persisted throughout the agent's lifecycle.

Let's understand what that actually means.

Imagine our research agent.

The user asks:

"Find information about LangGraph."

The agent executes:

1.  Understand the question.
2.  Search the internet.
3.  Receive search results.
4.  Analyze those results.
5.  Decide whether another search is needed.

But here's a problem.

**How does the agent keep track of what has happened so far?**

How does the next node know:

-   What the original question was?
-   What the search results were?
-   Whether another search is required?
-   What information has already been collected?

This is where state comes in.

Think of state as a shared dictionary containing the information
maintained by the workflow.

For example:

``` python
state = {
    "question": "What is LangGraph?",

    "search_results": [],

    "analysis": "",

    "needs_search": True,

    "final_answer": ""
}
```

Every node can access the relevant information in this state.

Let's see how this works.

### Step 1: LLM Node

The LLM examines the question.

It decides that internet access is required.

The state becomes:

``` python
{
    "question": "What is LangGraph?",

    "search_results": [],

    "analysis": "",

    "needs_search": True,

    "final_answer": ""
}
```

### Step 2: Search Node

The search node reads the question and performs a search.

It updates the state:

``` python
{
    "question": "What is LangGraph?",

    "search_results": [
        "Result 1",
        "Result 2",
        "Result 3"
    ],

    "analysis": "",

    "needs_search": True,

    "final_answer": ""
}
```

### Step 3: LLM Node Again

The LLM now receives the updated state.

It can access the search results.

It analyzes them and decides whether another search is necessary.

Suppose it doesn't need another search.

The state gets updated:

``` python
{
    "question": "What is LangGraph?",

    "search_results": [
        "Result 1",
        "Result 2",
        "Result 3"
    ],

    "analysis": "The collected results are sufficient.",

    "needs_search": False,

    "final_answer": ""
}
```

### Step 4: Final Answer Node

The final node reads the information and generates the response.

``` python
{
    "question": "What is LangGraph?",

    "search_results": [
        "Result 1",
        "Result 2",
        "Result 3"
    ],

    "analysis": "The collected results are sufficient.",

    "needs_search": False,

    "final_answer": "LangGraph is a framework..."
}
```

That's the basic idea.

🗃️ **State allows different nodes to share information and maintain the
context of the workflow as it executes.**

### 🧱 How do we define state in LangGraph?

The instructor uses a dictionary-like structure.

In modern LangGraph Python code, you commonly define the state using
`TypedDict`.

For example:

``` python
from typing import TypedDict

class AgentState(TypedDict):

    question: str

    search_results: list

    analysis: str

    needs_search: bool

    final_answer: str
```

Then:

``` python
from langgraph.graph import StateGraph

graph = StateGraph(AgentState)
```

Here:

-   `AgentState` defines the structure of the information.
-   `StateGraph` creates a graph that operates using that state.

One additional detail from the video:

### ➕ Overwriting vs. Adding to state

The instructor mentions that state can be updated in different ways.

**Overwriting:**

Suppose the current state contains:

``` python
{
    "analysis": "Initial analysis"
}
```

A node returns:

``` python
{
    "analysis": "Updated analysis"
}
```

The previous value gets replaced.

**Adding:**

Suppose the state contains:

``` python
{
    "search_results": ["Result 1"]
}
```

You might want to add another search result instead of replacing the
existing list.

LangGraph supports this through something called **reducers**.

For example:

``` python
from typing import Annotated
from typing_extensions import TypedDict
import operator

class AgentState(TypedDict):

    search_results: Annotated[
        list,
        operator.add
    ]
```

Now, when a node returns:

``` python
{
    "search_results": ["Result 2"]
}
```

The reducer combines it with the existing list.

The result becomes:

``` python
{
    "search_results": [
        "Result 1",
        "Result 2"
    ]
}
```

This is useful when an agent collects information over multiple
iterations.

# ⚙️ 5. Compiling the Graph

We've now understood:

1.  State: Information maintained throughout execution.
2.  Nodes: Components that perform operations.
3.  Edges: Connections between components.
4.  Conditional edges: Connections that determine the next step
    dynamically.

But defining these components doesn't automatically give us an
executable agent.

We need to compile the graph.

Think of compilation here as preparing the graph for execution.

The process looks like this:

``` text
       Define State
            |
            ▼
       Create Graph
            |
            ▼
        Add Nodes
            |
            ▼
        Add Edges
            |
            ▼
    Define Entry Point
            |
            ▼
      Compile Graph
            |
            ▼
       Execute Agent
```

Let's understand each step.

### Step 1: Create the graph

``` python
graph = StateGraph(AgentState)
```

### Step 2: Add nodes

``` python
graph.add_node("llm", llm_node)

graph.add_node("search", search_node)

graph.add_node("final", final_node)
```

We're registering our components with the graph.

### Step 3: Connect nodes

``` python
graph.add_edge("search", "llm")
```

This creates a normal edge.

For conditional routing:

``` python
graph.add_conditional_edges(
    "llm",
    decide_next_step
)
```

### Step 4: Define entry point

Where should the agent begin?

``` python
graph.set_entry_point("llm")
```

This tells LangGraph to start execution from the LLM node.

### Step 5: Compile

``` python
app = graph.compile()
```

Now we have an executable graph.

The instructor mentions something interesting here.

Once compiled, the graph behaves like a normal LangChain runnable.

That means we can use familiar execution methods.

**Invoke:**

``` python
result = app.invoke({
    "question": "What is LangGraph?",
    "search_results": [],
    "analysis": "",
    "needs_search": True,
    "final_answer": ""
})
```

This executes the graph and returns the final state.

**Stream:**

``` python
for step in app.stream(initial_state):
    print(step)
```

This allows us to observe the execution as the graph progresses.

Instead of waiting for the entire workflow to finish, we can inspect
individual execution steps.

# 🛠️ 6. How does this connect to LLM Function Calling?

Towards the end, the instructor mentions something important.

He says that many models need to support function calling when building
agents that use tools.

Let's understand why.

Imagine you give an LLM this instruction:

"Search the internet for the latest AI news."

A normal LLM can generate text explaining AI news.

But generating text and actually searching the internet are two
different things.

The LLM needs a mechanism to request that an external function be
executed.

This is called **function calling (also known as tool calling).**

For example, suppose we have a search tool:

``` python
def search_web(query: str):
    # Perform internet search
    return search_results
```

We make this tool available to the LLM.

Now, when the user asks:

"Find the latest AI news."

The LLM can return a structured tool call:

``` json
{
    "name": "search_web",
    "arguments": {
        "query": "Latest AI news"
    }
}
```

Notice something important.

The LLM hasn't actually searched the internet.

It has only requested that the search function be executed.

The application executes the function and returns its result to the LLM.

The overall process:

``` text
       User Question
             |
             ▼
            LLM
             |
             ▼
     Requests Search Tool
             |
             ▼
       Tool Execution
             |
             ▼
       Search Results
             |
             ▼
            LLM
             |
             ▼
        Final Answer
```

This is why tool-calling support matters when building agents.

The LLM needs to communicate structured instructions to the application.

**Important distinction:** Function calling isn't exclusive to
LangGraph. It's a capability provided by supported models and their
APIs. LangGraph helps orchestrate the tool execution and subsequent
decisions.

# 🔧 7. What is the relationship between LangChain and LangGraph?

Let's connect everything.

Imagine you're building a customer-support agent.

It needs to:

-   Understand customer questions.
-   Retrieve information from a knowledge base.
-   Check order information.
-   Cancel orders when authorized.
-   Generate responses.

You could use LangChain to build individual components.

For example:

  Component                  Technology
  -------------------------- -----------------
  Prompt templates           LangChain
  LLM integration            LangChain
  Vector store integration   LangChain
  Retrieval chain            LangChain
  External tools             LangChain tools
  Workflow orchestration     LangGraph
  Conditional routing        LangGraph
  State management           LangGraph

The relationship is complementary.

LangChain provides many of the building blocks.

LangGraph provides the machinery to connect them into stateful
workflows.

You don't have to choose one over the other.

They work together.

# 🧭 8. Putting everything together: The mental model

Let's return to our research agent.

The user asks:

"Research the latest developments in RAG and explain them."

Here's how the entire LangGraph architecture works.

  -----------------------------------------------------------------------
  LangGraph concept                   What happens in our research agent
  ----------------------------------- -----------------------------------
  State                               Stores the question, search
                                      results, analysis and final answer

  Node                                LLM, search tool, analysis function

  Normal edge                         Connects search results to the LLM

  Conditional edge                    Decides whether another search is
                                      necessary

  Cycle                               Allows repeated searching and
                                      analysis

  Entry point                         Determines where execution starts

  Compile                             Prepares the graph for execution

  Invoke                              Executes the complete workflow

  Stream                              Allows us to observe execution
                                      steps
  -----------------------------------------------------------------------

The entire execution:

``` text
                USER QUERY
                    |
                    ▼
               [LLM NODE]
                    |
                    ▼
             NEED INFORMATION?
                /       \
              YES        NO
               |          |
               ▼          |
          [SEARCH NODE]   |
               |          |
               ▼          |
          UPDATE STATE    |
               |          |
               ▼          |
            [LLM NODE] ◄──┘
               |
               ▼
         MORE SEARCH NEEDED?
            /        \
          YES         NO
           |           |
           ▼           ▼
        [SEARCH]   [FINAL NODE]
                       |
                       ▼
                  FINAL ANSWER
```

The agent can repeat the process until it decides it has enough
information.

That's the fundamental idea behind LangGraph.

I want you to retain these six concepts particularly well.

  Concept             Remember it as
  ------------------- ---------------------------------------------------------
  LangGraph           Framework for building stateful, cyclic agent workflows
  StateGraph          The graph that manages shared workflow state
  State               Shared information passed between nodes
  Nodes               Individual components that perform operations
  Edges               Connections that determine execution flow
  Conditional edges   Dynamic routing based on decisions
  Compile             Prepares the graph for execution

### One final conceptual distinction

Remember what we discussed when you first learned about AI agents.

An agent is not simply an LLM, and it isn't necessarily a predefined
pipeline.

A traditional pipeline might look like:

``` text
A → B → C → D
```

An agentic workflow might look like:

``` text
A → B → C
    ↑   |
    └───┘
```

The difference is that the agent can make decisions, revisit previous
operations, and change its execution path based on intermediate results.

🎯 **LangGraph gives us a structured way to build that behaviour.**

## 🚀 10. What comes next?

This chapter introduced the architecture. The next important concepts to
understand when learning LangGraph are:

1.  **MessagesState:** How conversational messages are maintained in
    graph state.
2.  **ToolNode:** How tools are executed inside a LangGraph workflow.
3.  **tools_condition:** How LangGraph determines whether an LLM wants
    to call a tool.
4.  **Tool calling loop:** How an LLM repeatedly calls tools and
    receives their results.
5.  **Checkpointing:** How graph execution state can be saved and
    resumed.
6.  **Human-in-the-loop:** How humans can interrupt and approve agent
    actions.

One particularly important thing: don't confuse the state of an
individual graph execution with persistent conversational memory.
Checkpointing and thread management are what allow LangGraph
applications to preserve state across separate interactions.

**My recommendation:** Before moving into multi-agent systems,
understand how to build a single agent with LangGraph that can call
multiple tools, maintain state, and decide when to stop.

That will give you the foundation to understand everything else without
blindly memorizing LangGraph APIs.
